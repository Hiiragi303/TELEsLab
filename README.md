# TELEsLab
自分に合った研究室を調べられる音声対話Bot　

## 1. はじめに
本レポートは、「実世界コンピューテングプロジェクト２」における最終課題として取り込んだ、研究室支援システム「TELEsLab」についてのレポートである。

### 1.1 レポートの目的
本レポートの目的は、大学における多様な研究室の中から個人に合った研究室を、音声対話を通じてユーザに必要な情報を提示し、研究室選択を支援する音声対話システムを設計・実装・評価することである。

### 1.2 何をしたレポートであるか
本システム「TELEsLab」では、研究分野、研究室の活動内容、および評価情報といった複数の観点から研究室を絞り込む対話を実現し、ユーザが会話の流れの中で自身に適した研究室の情報を取得できることを目指した。

---

## 2. 課題の概要
本課題の概要として、Botpressを用いて、自分に合った研究室検索と音声システムの開発をした。
### 2.1 課題設定
主に大学2年生が「全部の研究室をまわることはできないため、どの研究室が自分に合っているかを決めにくい」という課題を抱えている。これに対し、音声対話を通じて、個人の志向に合致した研究室を紹介するシステムを構築する。
### 2.2 要求仕様
- 検索機能: 分野タグ、作業量等のパラメータ、評価値による検索、また研究室の名前が可能であること。
- 対話の継続性: 1つの研究室を提示した後、続けて別の検索を行うか確認するループ構造を持つこと。
- 例外処理: 該当なしや曖昧な入力に対する聞き直し機能を備えること。

## 3. シナリオ作成
### 3.1 シナリオの収集
以下が、本システムで想定したシナリオのパターンである。

| No. | 検索パターン | シナリオの内容 |
|----|-------------|---------------|
| 1 | タグ検索 | ユーザが研究分野を指定し、該当する研究室一覧を表示した後、興味のある研究室を選択して詳細を表示するシナリオ。 |
| 2 | パラメータ検索 | ユーザが研究室の活動内容や支援体制などを指定し、条件に合致する研究室をランキング形式で提示した後、興味のある研究室を選択して詳細を表示するシナリオ。 |
| 3 | 評価検索 | ユーザが評価について指定し、満足度や評価情報に基づいて研究室を提示した後、興味のある研究室を選択して詳細を表示するシナリオ。 |
| 4 | その他 | ユーザが特定の研究室名を指定して詳細情報を取得する、または検索を行わずに対話を終了するシナリオ。 |

### 3.2 シナリオの分析
本システムでは各シナリオを評価するために、ブレーンストーミングおよびKJ法を用いた評価基準を検討した結果、以下の５項目を評価基準とした。<br>
1.自然（対話として成立しており不自然でないか）<br>
2.情報の明確さ（ユーザが求める情報が正しく取得できるか）<br>
3.効率性（無駄な会話が少なくシステムの目的まで簡潔であるか）<br>
4.柔軟性（さまざまな言い回しに対応できるか）<br>
5.音声認識（音声対話としての構造になっているか）<br>

## 6. 音声対話のテスト（システムテスト）
### 6.1 テスト概要
本章では、Node-Redで実装されている音声認識・音声合成を用いた対話インターフェースによって、本システムが正常に動作するかを確認することを目的とする。

テスト対象は以下の通りである。
- 音声認識の開始／停止
- 認識した音声のテキスト化

## 7. 考察
### 7.1 課題は解けたか（総合結論）
結論として、課題は要件通り解けたと考える。
理由としては、音声対話を通して、分野タグ、パラメータ、評価値、そして研究室名での検索をするという目的を果たせたからである。
さらに、検索結果に対応するグラフや、口コミを表示する機能もつけることができたため、満足のいく結果となったと考える。
よって、課題は解けたと考える。
### 7.2 システムの対話成立性の検討
音声認識の精度、認識結果が悪いという点である。
認識精度については今回の実装の範囲では無いため使用する技術選定段階の問題であるが、認識結果について、テキストのみの実装と比べ追加の対処が必要な部分があったため、処理を継続的に追加していく必要があると考える。
それに加え、音声入力を途切れさせることができていないため、会話のキャッチボールが上手くできない。
### 7.3 問題点と対策
本システムの開発およびテスト運用を通じて明らかになった主な問題点と、それに対する対策について述べる。

1.単語の音声認識精度の改善.     
・開発当初は、特定の研究室を指定する手段としてA研究室・B研究室といった短い単語による音声入力を採用していた。しかし、アルファベットや短い単語は音声認識の精度が低く、ユーザが意図した研究室とは異なる入力が反映される誤認識が多発した。この対策として、短い単語での識別を改め、音声認識でも正確に反応できる判別性の高い名称やフレーズへと変更を行った。

2.リアルタイム処理による応答遅延とデータ構造の見直し <br>
・現状のシステムでは、ユーザからのリクエストを受信するたびにデータベース内の全件に対してソート処理（並べ替え）を行っている。そのため、データ量が増加した場合に応答速度が低下する問題が確認された。 この対策としてリクエストごとの動的な処理負荷を軽減するため、あらかじめソート済みのデータセットを用意し、リクエスト時にはそれを参照して即座に返す仕組み（プリソートまたはキャッシュの利用）への移行が必要である。これにより、レスポンスタイムの大幅な短縮が見込まれる。

### 7.4 本実習で得た知識と技術
本実習を通じて、以下の2点の知識と技術を習得した。
1.音声対話システムの実装技術 
BotpressとGAS（Google Apps Script）、スプレッドシートを連携させたデータ通信処理と、HTML/JvaScriptを用いて検索結果をグラフやランキングとして視覚化するフロントエンド技術を身につけた。
2.チーム開発における管理手法 
「シックスハット法」を用いた多角的なアイデア出しや、バックエンド・フロントエンドの明確な役割分担を実践し、コミュニケーションを重視した円滑なチーム開発の手法を学んだ。
